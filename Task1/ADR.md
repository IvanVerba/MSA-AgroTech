### <a name="_b7urdng99y53"></a>**Название задачи:** Архитектура MVP системы мониторинга свинофермы компании «АгроТех Х»
### <a name="_hjk0fkfyohdk"></a>**Автор:** Иван Верба
### <a name="_uanumrh8zrui"></a>**Дата:** 07.12.25
### _**Контекст**_
<u>Цель бизнеса</u>: _Оценить проект MVP платформы мониторинга свиноводческих ферм, чтоб автоматизировать процессы, связанные с кормлением, безопасностью и мониторингом поголовья скота на нескольких фермах; с перспективой доработки до SaaS-решения для других компаний_
<br/>
<u>Технический контекст</u>: _Текущая архитектура компании «АгроТех Х» - [Цифровая платформа «АгроТех Х»](../agrotech.puml "Исходный локальный файл agrotech.puml"). Решить: какие текущие сервисы могут быть полезны, а какие необходимо будет добавить; какие в головном офисе и какие в сервисах-агентах на фермах_
<br/>
<u>Проблема</u>: _С одной стороны система должна представлять собой MVP-решение для надёжного мониторинга скота ограниченного количества ферм в условиях ненадёжного интернет. Тогда большая часть сервисов должна работать автономно непосредственно на ферме. С другой - заложить потенциал облачного SaaS-решения в мультитенантной архитектуре для других компаний. Тогда важно будет наоборот - приоритетно планировать сервисы в центре (и в перспективе в облаке) с максимальной доступностью. Таким образом важно при проектировании архитектуры MVP сразу учесть необходимость компромисса: вместо крайностей полностью централизованного или полностью автономного решения предложить гибридные варианты, которые отличаются только балансом(составом) сервисов в центральной платформы АгроТех и на ферме, и соответственно способами их взаимодействия._

### <a name="_qmphm5d6rvi3"></a>**Решение**

**Ключевая логика принятия решений:**
1. <u>Для предсказуемости и мимимизации затрат на MVP:</u> приоритетно переиспользовать технологии, уже работающие в цифровой платформе компании, но с учётом их открытости и перспективности развития уже полноценного продукта на их основе;  
2. <u>Для покрытия максимума запрошенных требований:</u> нужен компромисс по проблеме, обозначенной в Контексте (выше): баланс между автономностью ферм и централизованностью управления с перспективой тиражируемого SaaS-продукта.

**Решение 1.** Приоритет локальных вычислений (Edge на ферме).

[Диаграмма контекста C1_1](./C1_1.puml), [диаграмма контейнеров C2_1](../Task2/C2_1.puml)

* Сервер фермы - в роли IoT-шлюза (сбор/передача/маршрутизация данных/команд конечных устройств) и граничного(Edge) сервера обработки данных, инференса видеопотока (распознавание событий), БЛ обработки, HMI. Логика диспетчеризации,обработки, алертов в систему экстренных оповещений, собственный Web-UI(Dashboard) или расширенный HTTP API - на базе Node-RED (хорошо знаком разработчикам компании), инференс модели видеораспознавания (от партнёров), шина данных с мостом в центр - брокер MQTT (NanoMQ - поставить и настроить). 
* Метрики/аналитики/события при отсутствии связи автоматически накапливаются в локальную БД MQTT-брокера фермы, при наличии - передаются в Kafka центрального офиса через его Kafka connect и MQTT-мост брокера фермы NanoMQ (всё только настроить). Аналогично в обратную сторону - управляющие параметры и команды.


### <a name="_bjrr7veeh80c"></a>**Альтернативы**

**Решение №2.** Приоритет централизованных вычислений (центральный офис с перспективой переноса в облако).

[Диаграмма контекста C1_2](./C1_2.puml), [диаграмма контейнеров C2_2](../Task2/C2_2.puml)

* Облегчённый сервер/IoT-шлюз фермы: диспетчеризация потоков с устройств/видео в центр и команд управления через надёжный скоростной он-лайн. На случай сбоев - тот же MQTT-мост с буферизацией и минимальная аварийная БЛ обработки/отображения на Node-RED.  
* Переезд в центр (облако): инференс моделей, Node-RED с модулями обработки данных, управления, основной визуализации. 


**Общее в обоих вариантах:**
- Администрирование, обновление ПО, настройка прав доступа на фермах - силами сисадмина центрального офиса путём удалённого доступа (достаточно для MVP), в перспективе возможна автоматизация доставки настроек/обновлений.
- Существующие сервисы центрального офиса (Kafka, Хранилища данных, ERP, Аналитический модуль, BI-система, Web-портал) - дорабатываются/донастраиваются (напр. для 1С-ERP есть готовые расширения) для учёта данных свиноферм. Примерный объём доработок и данных должен быть сопоставим с таковыми для тепличных хозяйств (в компетенции разработчиков существующей центральной платформы)  
- Центральный сервис управления свинофермами (MES) - для управления параметрами процессов ферм, оперативные расчёты по кормам/продукции (сводить нормативы ERP и метрики с ферм). Разумно интегрировать в центральный Web-портал (с аналогичным стеком технологий)
- Возможность переноса/комбинирования вариантов размещения инференса моделей распознавания и обработчиков потоков показаний/команд (Node-RED) на ферме или в офисе в зависимости от условий и выбранной кофигурации разработки стартового MVP   

**Недостатки, ограничения, риски**
* **Решение 1:**
* Ферма автономна в плане мониторинга изнутри и оперативных процессов. Сложнее/дороже оснащение/обслуживание сервера.  
* **Решение 2:**
* Масштабировать центр с перспективами SaaS - легче. Риски и выше требования к каналам и серверам центра/облака.
